# DevFest 2026 Sanity Studio

このディレクトリは、DevFest 2026 のコンテンツ管理システム（Sanity Studio）のソースコードを含んでいます。Astro で構築されたサイトに対して、各都市（Tenant）のイベント情報、セッション、登壇者、ミートアップ、パートナー企業、および About ページのコンテンツを提供・管理するためのものです。

## 環境構築

開発を始める前に、依存パッケージをインストールしてください。リポジトリのルートではなく、この `studio/` ディレクトリ内で実行します。

```bash
pnpm install
```

## 環境変数

Sanity Studio を起動・デプロイするには、プロジェクトIDとデータセットの設定が必要です。
`studio/.env` ファイルを作成し、以下の環境変数を設定してください。

```env
SANITY_STUDIO_PROJECT_ID=あなたのプロジェクトID
SANITY_STUDIO_DATASET=production
```

「サイトに反映」がビルドの状況を読むリポジトリは `gdg-jp/devfest26` が既定です。fork した場合だけ次を足してください。**秘密ではありません** — `SANITY_STUDIO_` で始まる値はブラウザに配られるバンドルに埋め込まれるので、ここに秘密を書いてはいけません。

```env
SANITY_STUDIO_GITHUB_REPO=owner/repo
```

## ローカル開発サーバーの起動

以下のコマンドで Studio の開発サーバーを起動します。

```bash
pnpm dev
```

ブラウザで表示される URL（通常は `http://localhost:3333`）にアクセスし、コンテンツの編集・プレビューを行えます。

## デプロイ

変更を反映し、Sanity のホスティング環境（`*.sanity.studio`）にデプロイするには以下のコマンドを使用します。

```bash
pnpm deploy
```

## Presentation — プレビューを見ながら書く

**下書きプレビューの URL に `/studio` を付けて開いてください。** 左に編集フォーム、右にそのページのプレビューが並び、右の本文をクリックすると左の該当フィールドに飛びます。

**右が更新されるのは、入力の手が止まってからです。** Sanity は打っている最中の下書きも保存しにいくので、そのたびに右を描き直すと書きかけの文が一語ずつ出ることになります。1 秒静かになるまで待ってから、一度だけ更新します。すぐ見たいときは右上の更新ボタンを押してください。

**「Edit」を切った状態は、ページを移動しても続きます。** このスイッチはプレビュー側が持っている状態を映しているだけなので、本来はリンクをたどるたびに「入」に戻ります。切ったことをページ側で覚えておいて、読み込みのたびに戻しています。Studio がつながった直後にプレビュー側の枠がいったん作り直され、そのとき勝手に「入」へ戻ってしまうので、つながって落ち着いたところでもう一度切り直します（スイッチが一拍おいて「切」に落ち着くのはそのためです）。覚えているのはそのタブが開いている間だけなので、新しいタブで開けば「入」から始まります。Alt を押している間だけ枠を隠す使い方は、これまでどおりです。

Studio は 2 か所にあります。中身は同じコミットの同じソースです。

| どこ                         | 何のため                                            |
| ---------------------------- | --------------------------------------------------- |
| `devfest26.sanity.studio`    | ふつうに書くとき。これまでどおり                    |
| 下書きプレビューの `/studio` | **見ながら**書くとき。Presentation タブはこちらだけ |

Presentation タブが `devfest26.sanity.studio` に無いのは、意図的です。プレビューは GDG Accounts のサインインで守られていて、別サイトに埋め込まれた iframe にはそのセッションが渡らないため、あちらに置いても白い枠が出るだけになります。理屈は [`preview/README.md`](../preview/README.md) にあります。

### クリック編集が効くもの・効かないもの

- **効く**：タイトル、概要、経歴、リード文、本文、会場名、参加費、統計の数字とラベル、タイムテーブルの行 — つまりページに文章として出ている文字列
- **効かない**：**画像**と**参照**（セッションのトラック、セッションと登壇者の紐付けなど）。仕組み上、文字列にしか印を埋め込めません。左のフォームから編集してください
- **効かない**：日付、URL、スラッグ、色、`status` や `theme` のような選択肢。壊れると困る値なので、意図的に対象外にしています

ページに出ているのにクリックできない文字列を見つけたら、それは対象リストに入っていないだけです。[`src/preview/stega.ts`](../src/preview/stega.ts) に名前を足せば効くようになります。

### ドキュメントを開いたとき

Presentation は「このドキュメントはどの URL に出るか」を知っているので、セッションを開けばそのセッションのページに、トラックやパートナーを開けばその都市のトップに、プレビューが移動します。都市（`event`）が未設定のドキュメントでは移動先が無く、その旨が表示されます。対応表は [`presentation.ts`](presentation.ts) にあります。

## `event` ドキュメントは都市そのものです

`event` は「イベント情報」であると同時に**サイトのテナント設定**です。ここに入っている値が、そのままサイトの日時・会場・配色・トラック・ナビゲーションになります。

- `slug` がそのまま公開 URL になります（`/kansai`、`/tokyo` …）。**`portal` と `studio` は使えません** — 前者はルートの開催地一覧、後者は下書きプレビューが Studio 自身を置いているパスです
- **`event` を 1 件 publish すれば、その都市のページが増えます。** repo 側に登録する場所はありません。次のビルドで CI がこのドキュメントを見つけて、その都市のジョブを 1 つ増やします
- `theme` は DevFest のコアカラー 4 色からの選択式です。自由入力にしていないのは、ブランドガイドにない色が載るのを防ぐためです
- 日付ラベル（`2026年10月18日`、`10/18`、`SUN` など）は `startsAt` / `endsAt` から自動生成されます。表示用の文字列を入力する欄はありません
- 会場の住所欄は空のままで構いません。埋まるまで構造化データから住所ごと省略されます

**必須項目が空のまま publish すると、その都市のビルドだけが失敗します。** 「undefined」と書かれたページが公開されるより、ビルドが止まるほうが安全だという判断です。落ちるのはその都市のジョブだけなので、

- 他の都市は普通に公開されます
- その都市の `/<slug>` には**前回公開されたページがそのまま残ります**。消えたり 404 になったりはしません
- 開催地一覧のカードも出たままです

つまり、直すまでの間もサイトは前の状態で動き続けます。ただし `slug`・タイトル・テーマ・日付・会場のどれかが欠けている場合だけは別で、その都市は**一覧のカードごと出なくなります** — カードに印刷する項目そのものだからです。

## ⚠️ 重要な注意点：Event Reference について

Sanity 上で管理されるすべてのコンテンツ（セッション、登壇者、ミートアップ、パートナー、About ページ）は、**必ず所属する「Event（都市）」に関連付けられている必要があります。**

- 新しいドキュメントを作成する際、`Event` フィールド（Reference）を必ず設定してください。
- `Event` リファレンスが未設定のドキュメントは、どの都市のサイトにも表示されません。
- Desk Structure により、都市ごとにコンテンツがグループ化されています。**都市を選んでから「新規作成」すると `Event` が自動で入ります**ので、必ずこの導線を使ってください。

## 公開フロー

**公開と反映は別の操作です。** 公開してもサイトは変わりません。サイトを変えるのは「サイトに反映」だけです。

### 1. 公開する — 「まとめて公開」

**Publish は 1 クリックでは公開されません。** ボタンを押すと確認ダイアログが出ます。データセットは public なので、**公開した時点でサイトに出る前から API 経由で誰でも読めます** — ダイアログはそのことを言っています。

**複数の下書きは「まとめて公開」（左のツール一覧）でまとめて出してください。** 選んだものを 1 トランザクションで公開するので、「セッションは公開されたが登壇者はまだ」という途中の状態が生まれません。

- 行をクリックすると、右に**公開済みとの差分**が出ます（未公開のものは全項目が追加として並びます）。緑が増える値、赤が消える値です
- 未公開のドキュメントを参照している場合、確認ダイアログが**一緒に公開されるものを挙げます**。先に参照先だけ単独で公開しておく必要はありません
- 参照先がどこにも無いときは公開できません。参照を外すか、参照先を作り直してください

### 2. 反映する — 「サイトに反映」

サイトは静的なので、**作り直さないと公開した内容は出ません。**「サイトに反映」（左のツール一覧）が、その作り直しを始める唯一の入口です。

- **開催地ごとに選べます。既定では何も選ばれていません** — 反映は 1 開催地ずつのことが多いためです。選ばなかった開催地は作り直されず、今出ているページがそのまま残ります
- **「未反映 3 件」**は、その開催地の公開済みドキュメントのうち、最後の反映より後に変わったものの数です。下書きは数えません
- **トップページは必ず一緒に作り直されます。** カードがその開催地の `event` ドキュメントの中身を印刷しているためです
- ビルドとデプロイに数分かかります
- 下に**直近のビルド**が出ます。失敗したときは、どの開催地のどのステップで落ちたかと、原因の抜粋が並びます。生のログは GitHub 側でしか読めないので、足りないときは「GitHub で見る」を開いてください

**自動では反映されません。** 公開しただけで作り直すようにすると、1 日の編集がそのまま 1 日分のビルドになります（Sanity の webhook はドキュメント単位で飛ぶので、「まとめて公開」で 12 件出せば 12 回です）。代わりに、押し忘れると公開したものがサイトに出ないままになります。未反映の件数が並んでいるのはそのためです。

webhook をどう設定するかは[ルートの README](../README.md#公開フロー)にあります。
